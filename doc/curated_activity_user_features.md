# 精選池使用者功能 — 正式產品規格（2026-10-10）

**狀態：DESIGN APPROVED / IMPLEMENTATION NOT VERIFIED。** 本文件是「精選池資料進入 Life 之後」唯一正式使用者功能規格；當前 API / Flutter 已有**共用精選池基本瀏覽**，但下述兩入口、個人動作、預警和旅遊候選**尚未因此視為已實作**。實作狀態看 [CURRENT_STATE](CURRENT_STATE.md)、GitHub main 和真實 runtime。

## 邊界與共用資料

唯一最新核准入口：**ChatGPT 探索／核證 → Drive 精選池 → [獨立交接 Sheet](https://docs.google.com/spreadsheets/d/1OZdQPmypZ1zwB65K4oQOr3VBGP2GAFMmBnZsqAW5ob4/edit) → Life 每日 GCP Job → PostgreSQL curated pool → 使用者 UI**。Life 不做官網／文化部／TDX 掃描、來源 crawler、舊 Queue／claim／lease 或第二次 AI 評選。ACKED/ERROR 是匯入回執而非舊 Queue。詳見 [交接契約](curated_sheet_job_ingestion.md)；[原 API 契約](free_events_candidate_ingestion_contract.md) 是既有相容實作，不表示新 Job 已完成。

**共用一筆資料，不拆成兩個資料來源。** 同一活動可包含一般活動、限量場次或優惠，允許同時出現在兩個功能；可在後續版本設計母活動／子場次（相同原始 URL 可用既有 occurrence_key 區別），避免在清單間複製相同實體。精選不代表已核實可報名、尚有名額或保證優惠。

## 兩個獨立使用者功能入口

| 入口 | 主要目的 | 核心資訊 | 核心動作 | 行事曆預設語意 |
|---|---|---|---|---|
| **限時機會** | 不錯過可行動的機會；報名、預約、限量／限時優惠、名額、領券 | 開放時間、截止、條件、報名狀態、名額／庫存及證據（未知須顯示未知） | 追蹤、提醒、加入待辦；完成後可加入確定行程 | 行動時間點（開放、截止），與實際參與日分開 |
| **活動探索** | 發掘值得參加的活動與旅遊規劃中繼站 | 開始／結束日期、地點、內容、交通／來源（有資料才顯示） | 收藏、標記活動日期、加入未來旅遊候選 | 活動期間的資訊標記，不等於占用個人時間 |

使用者可由同一活動卡進入兩者，不得為互斥分類而遺失其報名機會。名額耗盡、取消、延期、報名窗口未知等情況需明確表達；未經來源證據不得自行推測精確時間或可用名額。

### 評級、時效與用途分離

**1–5 星價值**、需不需要動作、時間急迫性、是否適合旅遊、活動類別，彼此是獨立維度；不能把「五星＝要搶名額」或「一般活動＝低星」寫死。現有 curated schema 有 `importance`、`registration_required`、`registration_status`、`limited_offer`、`registration_deadline`，但尚缺獨立的使用者追蹤／提醒語意和開放時間等欄位。新增欄位前另做 additive migration 和契約驗證。

## 使用者自主動作（不因瀏覽自動建立）

從精選池卡片提供簡潔的「收藏／追蹤」「加入」入口，展開後可**分別勾選**：
- **追蹤提醒**：尤其是限時機會的報名開放／截止，可選提前預警；沒有可信開放時間，不排程假精確提醒，只允許不含捏造時間的追蹤／待確認。
- **建立待辦**：例如「10/14 開放後報名」。僅用於需要個人行動的事項；一般活動探索預設不建待辦。
- **加入行事曆**：選擇「活動日期標記」「報名／截止提醒」「確定參與行程」之一；活動範圍標記不得每日占滿 busy 時段。日期範圍未知時不建立假日程。
- **加入旅遊行程候選**：未來旅遊規劃功能的輸入；本期只保留契約／擴充點，不能假稱旅遊行程編排已完成。

預設四項均由使用者自行決定，不因精選入池、瀏覽、收藏、啟用功能或後台開關，自動寫入個人 Tasks／Google Calendar／通知訂閱。勾選和取消分開控制，同一來源重試不得重複建立個人項目；可由使用者決定保留、更新或刪除已有個人副本，且修改共用精選池時不能靜默覆寫已確認私人行程。

## 行事曆與通知語意

- **報名提醒**：有明確、含時區的開放／截止時間時，才可選提前一天、一小時或個人化間隔；提醒本身不代表已報名。
- **活動日期標記**：是資訊參考，可為全天日期或日期區間，不代表使用者確認參加、不得自動設為忙碌或創造一整個月的占用。
- **確定參與行程**：使用者明確確認後，使用其選定的實際日期／時段，可呈現在個人行事曆。
- **通知**：以偏好、政策、來源時間可信度與時區決定；失效／截止停止不當催促。Google Calendar 寫入需要每位使用者自己的 OAuth 與明確授權。Google API 失敗不可回報成功；重試需 idempotency。

限時機會可由使用者自行管理「想報名 → 等開放 → 已送出／待確認 → 成功／候補／失敗／取消」，但**狀態是使用者追蹤資訊，不是官方票務驗證**。未來報名成功後可加入旅遊行程；不得在 Life 內自動代報名、代搶票、支付或繞過名額限制。

## 產品導覽、個人與後台權限

- 手機沿用 Material 3 底部導覽，桌面使用左側 Rail／Sidebar；**兩個入口獨立受後台 feature rollout 控制**。使用者可在可用功能範圍內調整排序、釘選及首頁摘要卡片。
- 後台只可控制功能開放與全站精選池資料／操作錯誤，不能代用戶操作私人待辦、行事曆、通知或讀取其 Google 授權內容。
- 精選池公共資料與使用者個人追蹤、收藏、待辦、行事曆／旅遊候選完全隔離，依 `user_sub` 授權；寫入必須有權限、去重、audit，不能跨帳號顯示。
- Life 管理的 Drive AI Provider 與 ChatGPT 獨立探索、Google Drive 優惠研究工作完全分離。本次**不改 Drive 工作流**。

## 下一輪精選池產品交付契約（2026-10-10）

**範圍只限「ChatGPT 已精選、進入 Life 之後」的產品。** Life 不參與活動探索、來源清單、票務搜尋、開放資料查核、來源排程；這些研究資料只留在 Drive，不得因本規格而重新啟動採集 Job、Queue 或第二輪 AI 評選。**早發現、早預告是上游資料的價值，Life 負責清楚呈現並讓使用者採取自選行動。**

### A. 一主活動、一張主題卡、多個優惠／場次

- 以單一 PostgreSQL 精選池作共用資料；同一主活動內不同時間、報名入口、限量福利可以保存成不同子優惠／場次。畫面預設**一主活動一張卡**，卡內展開獨立的優惠、名額線索、報名開放／截止及實際活動日期；多票種不應膨脹成重複主活動。
- 顯示／使用者通知以主活動合併；同時同日開報的多個子優惠合併成一則提示，但仍提供每個子優惠的報名連結和時間。只有新增重要子優惠、開放／截止時點異動或狀態實質變化，才可依 `parent + offer + phase` 防重後重新告知；禁止單因同一活動出現在多來源而重複提醒。
- **現況資料契約差異：** `backend/app/api/curated.py` 的唯一鍵是 canonical `original_url + occurrence_key` SHA-256；既有 `occurrence_key` 可暫時區分共用網址的不同場次，但 **`parent_event_key`、獨立 `offer_key` 與主活動聚合尚未實作**。Drive 的 `event_key` 不能直接當資料庫 PK，也不能假設兩個不同 URL 會自動語意去重。新關聯欄位／獨立 child entity 是否必要，應用最小 additive schema migration 與兼容性測試實作，而非複製資料表或新開第二個活動池。

### B. 顯示真實情況，不要求 Life 盯即時庫存

- 精選的 5★ 可以是**「已核實即將開放」**或**「潛力待核預告」**；兩者都值得提前被看見。分開顯示重要性、資料證據等級、報名起點／截止、個人行動需求、活動日期；不把 5★ 當成 `open` 或有空位的證據。
- 展示「資料待核」「報名日期有衝突」「需先付可退保證金」等真實警示。**不用**在 Life 重新查票務平台的即時餘額／送出報名表／驗證能否結帳；未知就顯示未知並連回主辦原頁。
- **現有 API 不含** `registration_open_at`、`parent_event_key`、`offer_key`、來源證據與時點衝突、可退押金／實際不可退平台費等完整欄位，且 `registration_deadline` 不是開放報名時刻。導入新欄位時需兼容現有 `CuratedItemIn`、資料庫 0015、GET 列表與原始 source link，避免用 summary 的自由文字或不實的 `fee_amount` 偽造數值。先定最小必要欄位，配套 migration、驗證、序列化與測試。
- 費用顯示至少能區別免費、附條件免費、必要付款、先付可退押金／退款條件及自選消費；「可確定福利面額」與「推估福利／抽獎」不能混列確定價值。可退保證金活動不得因先繳 100 元便被 UI 排除。

### C. 使用者自選：待辦、日曆、提醒與旅遊候選

- **限時機會**優先顯示「我要報名／領取」及開放、截止時間；**活動探索**優先顯示活動開始／結束、地點、可加入旅遊候選。兩入口彼此可重疊，但不維護兩份活動資料。
- 只有使用者明確勾選，才能建立「報名待辦／預警」「活動日期資訊標記」「報名時間提醒」或「已確定參與行程」；前兩者不得被誤當已完成報名，資訊標記預設不占用行事曆 busy。未來旅遊行程編排只留擴充點。
- 個人追蹤或動作資料按 `user_sub` 隔離，需權限、可取消、重試去重、Google OAuth 失敗處理和操作紀錄。後台只決定入口 rollout 和公共資料政策，不能替使用者建立私人行事曆。**ChatGPT 對話內的探索預告／精選池卡片，不等同已送達 App 推播。** App 通知需另開發並實測。

### D. 下一步開發與驗收順序

1. **P0 接入基線先驗：** 由真實 Drive「交接資料」輸出合格 READY（event_key/content_hash），驗證 Life Job 讀取、PostgreSQL 重送不重複／網址更換映射、版本一致 ACKED、owner/Flutter 讀回；缺少 runtime 證據仍標 NOT VERIFIED。直寫 API 只能算相容性驗收，不可替代新交接 E2E。
2. **P1 共用資料模型與展示：** 先落地最小主活動／子優惠聚合，能區別「待核預告／已核實將開放／過期」和各自日期、來源、退款/押金；依需要做 additive migration、schema/API tests 與既有資料兼容；完成「一主題卡、多優惠展開」。
3. **P1 兩個使用者入口：** 實作限時機會／活動探索獨立導覽及交叉呈現，後台開放與使用者排序；保持篩選、loading/error/unknown、行動裝置/桌面一致。
4. **P1 個人動作：** 在有權限和資訊足夠時讓使用者勾選 Task、Calendar 資訊標記／報名提醒、通知訂閱；測試取消、重複加入、不同使用者資料隔離、日期時區及 Google 授權失敗。旅遊候選維持未來擴充。
5. **逐項驗收：** source/tests/CI、候選部署、runtime、真實 owner E2E 與個人 OAuth；使用 PASS／FAIL／NOT VERIFIED。**規格完成≠API擴充完成≠正式通知已上線。**
