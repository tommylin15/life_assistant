# Taiwan Activity Curated Pool — Approved Drive Sheet → Life Import

**Approved pipeline (2026-10-10):** ChatGPT explores, verifies and curates activities in the native Google Sheet named \`台灣活動｜精選池（Excel相容）\`, tab \`精選活動\`. Google Cloud Scheduler triggers a least-privilege Cloud Run Job which reads one known Sheet ID, performs deterministic Pydantic validation/dedup and reuses Life's existing PostgreSQL curated upsert. No AI inference in Life, no scanner, queue, Drive writeback, or MCP is required for this ingestion.

- Use \`LIFE_CURATED_SHEET_ID\` in the Job configuration, never derive the file from names or search across Drive. The Sheet is in the authorized \`life_assistantGPT\` Drive hierarchy. It is native Google Sheets, **not XLSX**.
- Google Sheets API read with job service-account Application Default Credentials, scope \`spreadsheets.readonly\`. Share **only that spreadsheet** with the job's service account as **Viewer**; do not make it public or create SA JSON keys. CI/CD deployer must have only minimum roles for job and scheduler management.
- Row gate: \`pool狀態\` exactly \`selected\` or \`changed\`. \`expired\`, \`cancelled\`, \`suspended\`, drafts and blank status do not write. Required: unique \`event_key\`, title, valid original **official** HTTPS URL or registration URL, valid 1–5 importance. No discovery/aggregation fallback.
- Identity is normalized official/registration URL + deterministic occurrence key derived from the sheet \`event_key\`. Repeated unchanged imports skip Postgres writes; changed rows use the existing validated \`ingest_curated_batch\` and auditable PostgreSQL \`ON CONFLICT\`. It is not a semantic cross-site duplicate resolver. If the official URL changes, the existing URL-based identity can change too and needs manual reconciliation.
- Unknown fees, registration status and limits stay unknown. Only official-verified values from explicit columns map into DB. No second AI check. No automatic personal tasks, calendar or alerts.
- Invalid approved rows are skipped with row count only (not private content); job exits nonzero to avoid reporting full success. Already-validated rows may commit before the job exits; re-run is idempotent. Batch is limited to 1000 sheet rows (including header), and updates are chunked at 40 events. No destructive deletion or cancellation propagation in this first iteration.
- \`LIFE_CURATED_IMPORT_APPLY\` defaults off. \`LIFE_CURATED_IMPORT_APPLY=1\` explicitly enables DB writes. Development/CI uses a synthetic sheet input and PostgreSQL sidecar; production run requires source permission, schema \`20261010_0015\`, release-image pin, real readback and Flutter display. Enable Scheduler only after staging acceptance and explicit configuration.
- The first file review on 2026-10-10 found 53 \`selected\` entries, one without official/registration URL. This is a **read-only observation**, not an import run or DB readback.

**Release sequence:** code/tests -> normal \`main\` four-job CI -> automatic staging-only app release -> manually deploy candidate Job pinned to the same validated GHCR digest, with database settings and dedicated read-only Sheet viewer identity -> dry-run -> staging apply -> PG readback and Flutter card -> separately enable Cloud Scheduler with OIDC to the Cloud Run Jobs \`run\` API. A normal app release must not silently enable any new scheduled writes. Record exact run ID, status \`PASS/FAIL/NOT VERIFIED\` and imported/unchanged/invalid counts.

The previously developed private Life Curator Plugin/MCP adapter is **not part of the active ingestion path**. Do not schedule it or infer ChatGPT Scheduled Tasks support. The old retired Ministry of Culture/TDX jobs remain disabled.
